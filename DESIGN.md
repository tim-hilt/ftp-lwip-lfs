# Design Notes

Rationale behind the behaviour of `ftp_server.c` — why the server answers the way it does, and which RFC requirement or lwIP/littlefs detail forced the choice. For the user-facing API, configuration and build instructions see [README.md](README.md).

## Resource model

- Designed for constrained targets: no dynamic allocation beyond the static `s_sessions[FTP_SERVER_MAX_CLIENTS]` table.
- No `<stdio.h>` or `<stdlib.h>`. `snprintf()` and `strtoul()` were the only users, and on a typical newlib target `snprintf` alone drags several KB of `vfprintf` into an image whose whole point is to be small. The replies and listing entries that need formatting are built with `ftp_put_str()`/`ftp_put_uint()` — a bounded cursor-and-limit pair that clamps instead of overrunning — and `ftp_parse_port_arg()` reads its own digits, which also makes it reject the leading whitespace and sign that `strtoul()` accepts but RFC 959 HOST-PORT syntax does not. `FTP_SERVER_DATA_BUF_SIZE` and `FTP_SERVER_PATH_MAX` have `#error` floors so a small override cannot break the buffer arithmetic these rely on.
- Each session's LFS file cache buffer (`FTP_SERVER_FILE_CACHE_SIZE`) must be >= `lfs_config.cache_size`; `ftp_server_init()` returns `ERR_ARG` otherwise.
- Only one data connection is active per session at a time. A transfer command issued while another is still pending is answered `450 Transfer already in progress`; `PASV` and `ABOR` both reset the state.
- A connection arriving with every session slot taken is answered `421 Too many users, try again later.` and closed, rather than reset.
- The `lfs_file_t` and `lfs_dir_t` of a session share their storage. Only one can ever be open — `ftp_transfer_busy()` refuses a transfer command while either is, and no command opens both — so a union saves an `lfs_dir_t` (40–56 bytes) per session for free. The `file_open`/`dir_open` flags say which member is live, and `ftp_release_transfer()` closes exactly one of them.
- Idle sessions are dropped after `FTP_SERVER_IDLE_TIMEOUT_POLLS` `tcp_poll` intervals. Traffic on either the control *or* the data connection counts as activity, so a long transfer is never cut short — only a stalled one.

## Data transfers

- Transfers are byte-transparent: no CRLF translation is performed in either direction. `TYPE A` and `TYPE I` are both accepted (RFC 959 §3.1.1.1 makes ASCII mandatory and the default) with an optional `N` format parameter, and behave identically — the reply to `TYPE A` says so rather than claiming a conversion that does not happen. Every other type is refused with `504`. `MODE` and `STRU` are accepted for their RFC 959 §5.1 default values (`S` and `F`) and refused with `504` otherwise.
- A send that lwIP cannot queue at all is retried from a `tcp_poll` on the data connection. `tcp_write()` returns `ERR_MEM` both for a full send window — where the peer's ACK brings the `tcp_sent` callback along to resume the transfer — and for an exhausted pbuf/segment pool, where it queues nothing, so no ACK and no `tcp_sent` ever follow. Without the poll a `RETR`/`LIST` unlucky enough to hit the second case would sit untouched until the idle timeout killed the whole session.
- Listing entries are queued with one `tcp_write()` each but pushed with a single `tcp_output()`, so lwIP can coalesce a directory's worth of ~55-byte lines into full segments instead of dribbling out one per entry.
- A client that opens the data connection and starts sending before its `STOR` has been processed does not lose the head of the upload: the pbuf is refused rather than discarded, which parks it in lwIP's `pcb->refused_data` until the command arms the transfer (`tcp_fasttmr` re-offers it every 250 ms). Costs no buffer of its own, and does not count as activity, so a connection that only ever sends unsolicited data still hits the idle timeout.
- A filesystem error part-way through a transfer ends it with `451`; a data-connection reset, an unusable data socket, or a download the client closes early all end it with `426` — never a misleading `226`. A client closing the data connection only means "transfer complete" for an upload (`STOR`), and only if the final `lfs_file_close()` flush succeeds — littlefs writes the tail of a file there, so a volume that fills up on the last chunk is reported as `451` rather than `226`. `ftp_data_recv()` cannot distinguish a client's clean half-close mid-`RETR` from a give-up: TCP delivers both as a FIN with no more data expected. Answering `426` for both is the deliberate, conservative choice — a half-close during a download is not part of the FTP protocol's own "file received" signal (that is `STOR`'s `lfs_file_close()` above), so there is no case where treating it as `226` would be correct.
- Every command gets exactly one reply, which constrains how a failed active-mode `tcp_connect()` is cleaned up. lwIP leaves that PCB in the `CLOSED` state, and `tcp_abort()` on it reaches `tcp_free()` and then `TCP_EVENT_ERR` — fired unconditionally in the raw-callback build (`tcp_priv.h`) — which would re-enter `ftp_data_err()` and answer `426` for the armed-but-never-announced transfer, immediately ahead of the `425`. The client would read the `426` as the answer to its `RETR` and match the stray `425` to whatever it sent next. The PCB therefore goes through `ftp_close_data()`, which detaches the callbacks before closing.
- That same failed `tcp_connect()` is also why the data PCB is `tcp_bind()`-ed to port 0 first. `tcp_connect()` assigns `pcb->local_port` from `tcp_new_port()` and only registers the PCB on `tcp_active_pcbs` once the SYN is enqueued; if that last step fails (`ERR_MEM`, empty segment pool) the PCB is left `CLOSED` with a non-zero local port and on no list at all. `tcp_close_shutdown()`'s `CLOSED` case then runs `TCP_RMV(&tcp_bound_pcbs, pcb)` unconditionally for such a PCB (`tcp.c`), whose debug build asserts `*pcbs != NULL` — so cleaning up after the failure trips lwIP's own assertion whenever nothing else happens to be bound. Binding first puts the PCB on that list and makes both outcomes well-defined; lwIP picks the same ephemeral port either way.
- A completed `RETR`/`LIST` is announced `226` only if its data connection could be closed gracefully. `tcp_close()` fails when lwIP cannot allocate the segment carrying the FIN, and `ftp_close_pcb()` then falls back to `tcp_abort()`, which resets the connection and discards whatever the peer had not yet acknowledged — so the reply is `426` instead. Beyond that the server does not wait for the last byte to be ACKed before replying: TCP itself is the client's completeness signal, since data that never arrives means the client sees an RST rather than a clean EOF on the data connection, and every client treats that as a failed transfer regardless of what the control channel said.
- A `LIST` entry that does not fit `FTP_SERVER_DATA_BUF_SIZE` is clamped, with the closing `CRLF` reserved up front so it survives. A line is 45 bytes of fixed columns plus the name plus the `CRLF`, and the `CRLF` is the first thing truncation would drop — without it the shortened name runs into the following entry and the client parses one mangled line instead of two. Reachable only at or below `47 + LFS_NAME_MAX`, so not at the default 512-byte buffer with `LFS_NAME_MAX` at 255.
- A transfer is never fed to a data connection whose handshake is still outstanding. lwIP's `tcp_slowtmr` polls every PCB on `tcp_active_pcbs` — a `SYN_SENT` one included (`tcp.c`) — and `tcp_write()` accepts `SYN_SENT` (`tcp_out.c`), so the `tcp_poll` above would otherwise run an active-mode `RETR` into a connection the client never accepted and answer `226` for it, ahead of the `150` that is supposed to come first. An FTP client behind a firewall that drops the inbound SYN is exactly this case, and lwIP retransmits the SYN for several seconds. `ftp_send_next_data()` refuses to serve a `data_connecting` session, which covers both the poll and `tcp_sent`.

## Security

- Both data-connection directions are pinned to the client ([RFC 2577](https://www.rfc-editor.org/rfc/rfc2577)): `PORT` only accepts the control connection's own peer address (FTP-bounce mitigation, `501` otherwise), and a `PASV` data connection arriving from any other host is dropped, so nobody on the network can race the client onto the passive port and take over the transfer. If the peer cannot be determined, both fail closed. Since that address is the only one `PORT` accepts, it is not stored per session either — `ftp_begin_transfer()` re-reads it from the control connection when it connects.
- `PORT` also refuses a data port below 1024 (RFC 2577 §3). The address check alone still leaves every privileged service *on the client's own host* reachable from the server's address with attacker-chosen payload, and port 0 is not a listening endpoint at all. No FTP client binds a privileged port for a data connection.
- Failed logins are counted per control connection; after `FTP_SERVER_MAX_LOGIN_ATTEMPTS` (default 3) the connection is answered `421` and dropped (RFC 2577 §5). Without a limit the only bound on a guessing run is the idle timer, and every guess resets it. A successful login in between deliberately does not clear the count — the limit bounds the connection, not one attempt sequence — and it is not a lockout: a legitimate user simply reconnects.
- Those two checks compare whole `ip_addr_t` values with `ip_addr_cmp()`, never an IPv4 `u32`. In a dual-stack lwIP, `ip_addr_get_ip4_u32()` renders *every* IPv6 address as `0` (`lwip/ip_addr.h`), so flattening the two peers before comparing them makes any two IPv6 hosts look like the same host — which lets an unrelated IPv6 machine take delivery of a `RETR` — and makes `PORT 0,0,0,0,p1,p2` match an IPv6 client. `ip_addr_cmp()` compares the address family too, so `PORT` (whose syntax can only name an IPv4 host) is refused outright on a non-IPv4 control connection.
- `PASV` refuses a control connection whose local address is not IPv4, with `421`. The `227` reply has room for four IPv4 octets and nothing else, and the alternative — advertising the `0,0,0,0` that flattening produces — points the client at the wrong host entirely. [RFC 2428](https://www.rfc-editor.org/rfc/rfc2428) `EPSV` is the extension that covers IPv6; it is not implemented. In an IPv4-only lwIP the guard is a compile-time constant and costs nothing.
- `FEAT` and `OPTS` are the only commands besides `USER`, `PASS` and `QUIT` accepted before login; see below.
- When both `FTP_SERVER_USER` and `FTP_SERVER_PASS` are configured, every `USER` is answered `331` and the verdict is deferred to `PASS` ([RFC 2577](https://www.rfc-editor.org/rfc/rfc2577) §3). There is only ever one valid user name, so rejecting a wrong one at `USER` would hand it to an attacker for free. With `FTP_SERVER_USER` alone there is no later step to defer to, and `USER` necessarily answers `230`/`530` outright.
- `FEAT` is answered before login (RFC 2389 §3) — clients use the feature list to decide what to send during the login sequence. `OPTS` is accepted there too, being the other half of that exchange: the standard opening is `FEAT`, then `OPTS UTF8 ON`, then `USER`, so gating `OPTS` behind credentials rejects a client for acting on what `FEAT` just advertised. It grants nothing — a bad option is still `501`, and everything else needs credentials.
- A pending `RNFR` is cancelled by any intervening command, including `USER`, `PASS` and `QUIT`, so a rename cannot survive a re-login and be completed under different credentials.

## Protocol handling

- Telnet control sequences are stripped from the control connection before a command is parsed. RFC 959 §4.1 has clients precede an in-transfer command with `IAC IP` + `IAC DM`, and lwIP delivers those bytes inline, so without this every conforming `ABOR` would read as an unknown command.
- Pathnames in `257` replies (`PWD`, `MKD`) are quoted with the RFC 959 Appendix II quote-doubling convention, so a name containing `"` still parses. A quoted form too long for the shared reply buffer is shortened rather than given a second `FTP_SERVER_PATH_MAX` of static RAM, and a doubled quote is dropped whole: emitting only its first half would leave the escape unbalanced, and the client would then read the closing quote as the second half of an escaped one and never find the end of the name. Whether the cut-off lands mid-pair depends on the parity of the reply's fixed text and of the name, so both `257` replies are tested at both alignments.
- `DELE` refuses directories and `RMD` refuses regular files, even though littlefs removes both with `lfs_remove()`.
- `RNTO` reports a missing `RNFR` (`503`) before it complains about its own argument (`501`). With no rename pending the fault is the command sequence, and the client's next move is to send `RNFR` — not to retry `RNTO` with a filename.
- `PASS` sent to a session that is already logged in — because authentication is disabled, or because `FTP_SERVER_USER` alone got the client in — is answered `230`, not `503`. Clients only send `PASS` after a `331`, but scripted ones send both unconditionally, and refusing a password the server never wanted turns a working configuration into a login failure.
- Active-mode data connections are opened from an ephemeral local port, not from `L-1` (port 20) as RFC 959 §3.2 describes. Binding port 20 for every transfer needs `SO_REUSE` and a `TIME_WAIT` PCB per transfer, which is not a trade a constrained target should make; no client in practice checks the source port.
- Path resolution normalises `.`/`..` straight into the result buffer, so `FTP_SERVER_PATH_MAX` bounds the *resolved* path: `CWD ../short` works from a directory too deep for `cwd + "/../short"` to fit. A single component that cannot itself be buffered is still rejected with `550`.
- `session->ctrl_aborted` / `data_aborted` are the one invariant in this file a contributor must not break by hand: they exist only so a callback still running when its PCB is torn down (a `tcp_abort()` inside another callback's call stack, most commonly) can tell it must not touch that PCB again, since lwIP has already freed it. Every path that can trigger such a teardown mid-callback has to set the matching flag before returning, and every callback that resumes after a call that might have torn down its own PCB has to check it before doing anything else. There is no compiler or lwIP assertion that catches a missed pair — it manifests as a use-after-free that only reproduces under the specific re-entrancy that triggered it, which is why every reset point and return site for these two flags was enumerated and checked by hand rather than left to be rediscovered by a future bug report.
